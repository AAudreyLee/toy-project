# 기능 검사 (verify-features)

바뀐 UI 코드의 버튼·폼이 의도대로 동작하는지 증명한다. 읽기만 하지 않고, 테스트로 남기고 실행해서 확인한다.

## 절차

1. **범위 정하기** — 인자가 없으면 작업 트리의 변경분(`--changed`), 커밋 직후라면 `git diff HEAD~1`로 본다. 전체 점검 요청이면 전체를 본다.
2. **상호작용 목록 뽑기** — `node scripts/list-interactions.mjs --changed`
   - `MISS`는 같은 라벨을 다루는 테스트가 없는 요소다. `OK`는 라벨이 테스트에 나오지만 동작까지 확인한다는 뜻은 아니므로, 바뀐 핸들러라면 해당 테스트를 읽고 실제로 클릭 후 결과를 단언하는지 본다.
3. **핸들러 읽기** — `MISS`와 바뀐 요소마다 연결된 핸들러(상태 변경, fetch 호출, 이동, 다운로드)를 읽고 "누르면 무엇이 일어나야 하는가"를 한 줄로 정리한다. 스펙(`docs/specs/`)이 있으면 수용 기준과 대조한다.
4. **테스트 보강**
   - 기본은 Vitest + Testing Library 컴포넌트 테스트(`*.test.tsx`, 대상 옆에 둔다). `app/page.test.tsx`의 `userEvent` + `fetch` stub 패턴을 따른다.
   - 여러 화면에 걸친 주 경로이거나 실제 브라우저가 필요한 경우만 `e2e/*.spec.ts`에 추가한다.
   - 외부 API(Azure OpenAI 등)는 호출하지 않고 stub한다. 단언은 "클릭 후 사용자에게 보이는 결과"로 쓴다.
5. **실행** — `bash scripts/verify.sh` (E2E까지는 `--e2e`). 실패하면 원인이 앱 코드 버그인지 테스트 오류인지 구분해서 앱 버그는 고치지 말고 보고하거나(요청 범위 밖이면) 고친다.
6. **보고** — 아래 형식으로 짧게.

## 보고 형식

- 검사한 요소 수 / 통과 / 새로 추가한 테스트
- 실패 또는 의심 동작: `파일:줄`, 기대 동작, 실제 결과
- 아직 테스트가 없고 이번에 다루지 않은 요소

## 자동 실행

- `core.hooksPath=.githooks` 이면 커밋 때 `scripts/verify.sh --staged`가 돈다(타입·린트·테스트 실패 시 커밋 차단, 커버리지 공백은 경고). 처음 클론했다면 `bun run hooks:install`.
- 건너뛰기: `SKIP_VERIFY=1 git commit ...` (사용자가 요청할 때만).

## 하지 말 것

- 스펙이 요구하지 않은 보안 하드닝·엣지케이스 테스트 추가 (AGENTS.md의 검증 예산).
- 런타임 확인을 Playwright 스크립트로 대신하기 — 실행 중인 앱 확인은 `next-dev-loop`.
