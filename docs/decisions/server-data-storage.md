# 만들어진 시스템의 서버 저장

## Decisions

- agent가 만든 시스템이 서버에 저장하는 데이터는 사용자 본인의 Supabase 계정에 둡니다. 시스템 하나마다 새 Supabase 프로젝트를 하나씩 만들어, 저장소·Vercel 프로젝트·데이터베이스가 1:1:1로 대응합니다(2026-11-19 사용자 결정).
- 사용자는 Supabase 액세스 토큰을 직접 붙여 넣어 연결하고, agent가 그 토큰으로 프로젝트와 표를 만들어 접속 정보를 Vercel 프로젝트의 환경 변수에 넣습니다. 토큰은 [credential-storage](credential-storage.md)를 따라 브라우저에만 보관합니다.
- 서버에 저장하는 데이터는 로그인 없이 주소를 아는 모두가 같이 보고 쓰는 공유 데이터입니다. 데이터베이스에는 생성된 서버 코드만 비밀 키로 접근하고, 브라우저가 데이터베이스에 직접 붙지 않습니다.
- 사용자별 비공개 데이터는 로그인이 필요하므로 지원하지 않습니다.

## Boundaries

- 이 결정은 만들어진 시스템의 데이터에만 적용됩니다. 이 서비스 자체의 진행 기록과 접근 권한은 [credential-storage](credential-storage.md)와 브라우저 저장소를 따릅니다.
- 데이터베이스 접속 정보(비밀 키, 비밀번호)는 사용자 환경 변수에만 두고, 저장소 코드나 브라우저로 내려가는 코드에는 넣지 않습니다.
- Supabase 토큰의 범위, 데이터베이스 지역, 표 구조는 이 결정이 정하지 않습니다.

## Why

사용자가 만든 시스템의 자원은 사용자 계정에 둔다는 방향([deployment-ownership](deployment-ownership.md))을 데이터까지 넓힌 것입니다. Vercel Marketplace의 데이터베이스(Neon 등)는 사용자 팀에 연동을 한 번 설치해야 하는데 이 설치를 API로 대신할 수 있는지 문서로 확인되지 않았고, Supabase 문서는 Marketplace 경로의 프로젝트 생성이 대시보드에서만 가능하다고 적습니다. 반면 Supabase Management API(`POST /v1/projects`)는 액세스 토큰으로 프로젝트를 만들 수 있어, 토큰 하나로 비개발자가 대시보드를 오가지 않고 끝낼 수 있습니다. 로그인을 빼는 것은 사용자별 권한 규칙과 생성 코드의 보안 검증 부담이 한 번에 만들 결과에 비해 너무 커서입니다.

## Reconsider when

- 토큰 발급 단계에서 비개발자가 이탈한다는 실제 사용 근거가 나올 때(Supabase OAuth 연결을 검토)
- 무료 플랜의 프로젝트 수 한도에 부딪혀 시스템을 못 만든다는 실제 사용 근거가 자주 나올 때(프로젝트 하나를 여러 시스템이 나눠 쓰는 방식을 검토)
- 로그인이 들어오는 결과를 shape할 때

## Still-rejected alternatives

- Vercel Marketplace의 Neon(Postgres) — 사용자 팀에 연동을 먼저 설치해야 하고 그 설치를 API만으로 넘길 수 있는지 확인되지 않았습니다. 같은 Vercel 토큰으로 끝낼 수 있다는 장점이 있어, API로 설치까지 되는 것이 확인되면 다시 검토합니다.
- 사용자가 Supabase 대시보드에서 직접 만들고 연결 값만 입력 — 비개발자에게 입력할 값이 많아 실수하기 쉽습니다.
- 프로젝트 하나를 여러 시스템이 나눠 쓰기 — 하나의 비밀 키로 모든 시스템의 데이터에 접근하게 되어 경계가 흐려집니다. 무료 한도 문제가 확인되면 다시 검토합니다.
- 로그인까지 함께 지원 — 사용자별 권한 규칙과 생성 코드의 보안 검증이 이번 범위를 넘습니다.
- Vercel Blob·Redis 같은 단순 저장소 — 표 형태의 데이터(목록, 조회, 수정)를 다루기 어려워 만들 수 있는 시스템이 좁아집니다.
