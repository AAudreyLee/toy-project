# 만들어진 시스템의 서버 저장

## Decisions

- agent가 만든 시스템이 서버에 저장하는 데이터는 사용자 본인의 Vercel 팀에 Vercel Marketplace의 Neon(Postgres)으로 둡니다. 시스템 하나마다 새 데이터베이스를 하나씩 만들어, 저장소·Vercel 프로젝트·데이터베이스가 1:1:1로 대응합니다(2026-11-19 사용자 결정. 사용자가 Supabase를 쓰지 않기로 했습니다).
- 데이터베이스 생성과 프로젝트 연결(접속 정보의 환경 변수 주입)은 사용자가 이미 입력하는 Vercel 토큰으로 agent가 합니다. 새 토큰이나 새 계정은 늘리지 않습니다.
- 사용자 팀에 Neon 연동이 처음 설치될 때 필요한 약관 동의는 사용자가 Vercel 대시보드에서 한 번 직접 합니다. 서비스는 설치 여부를 확인하고 안내합니다.
- 서버에 저장하는 데이터는 로그인 없이 주소를 아는 모두가 같이 보고 쓰는 공유 데이터입니다. 데이터베이스에는 생성된 서버 코드만 비밀 키로 접근하고, 브라우저가 데이터베이스에 직접 붙지 않습니다.
- 사용자별 비공개 데이터는 로그인이 필요하므로 지원하지 않습니다.

## Boundaries

- 이 결정은 만들어진 시스템의 데이터에만 적용됩니다. 이 서비스 자체의 진행 기록과 접근 권한은 [credential-storage](credential-storage.md)와 브라우저 저장소를 따릅니다.
- 데이터베이스 접속 정보(비밀 키, 비밀번호)는 사용자 Vercel 프로젝트의 환경 변수에만 두고, 저장소 코드나 브라우저로 내려가는 코드에는 넣지 않습니다.
- 데이터베이스 지역, 플랜, 표 구조는 이 결정이 정하지 않습니다.
- Neon 연동의 첫 설치를 API로 대신할 수 있는지는 확인되지 않았습니다. 확인 전까지는 사용자가 대시보드에서 한 번 설치하는 단계를 둡니다.

## Why

사용자가 만든 시스템의 자원은 사용자 계정에 둔다는 방향([deployment-ownership](deployment-ownership.md))을 데이터까지 넓힌 것입니다. 사용자가 Supabase를 쓰지 않기로 했고, Neon은 이미 연결하는 Vercel 토큰 하나로 생성·연결·환경 변수 주입이 되어([문서](https://vercel.com/docs/rest-api/integrations/create-integration-store-free-and-paid-plans)) 비개발자가 넣을 값이 늘지 않습니다. 무료 플랜은 요청에서 빼면 자동으로 골라지고, 결제 수단이 없는 계정은 402 오류가 날 수 있습니다. 로그인을 빼는 것은 사용자별 권한 규칙과 생성 코드의 보안 검증 부담이 한 번에 만들 결과에 비해 너무 커서입니다.

## Reconsider when

- Neon 연동 설치와 약관 동의를 대시보드에서 해야 하는 단계에서 비개발자가 이탈한다는 실제 사용 근거가 나올 때
- 무료 플랜의 데이터베이스 수 한도에 부딪혀 시스템을 못 만든다는 실제 사용 근거가 자주 나올 때(프로젝트 하나를 여러 시스템이 나눠 쓰는 방식을 검토)
- 로그인이 들어오는 결과를 shape할 때

## Still-rejected alternatives

- Supabase — 사용자가 쓰지 않기로 했습니다. 별도 계정과 토큰이 하나 더 필요했습니다.
- 데이터베이스 하나를 여러 시스템이 나눠 쓰기 — 하나의 비밀 키로 모든 시스템의 데이터에 접근하게 되어 경계가 흐려집니다. 무료 한도 문제가 확인되면 다시 검토합니다.
- 로그인까지 함께 지원 — 사용자별 권한 규칙과 생성 코드의 보안 검증이 이번 범위를 넘습니다.
- Vercel Blob·Redis 같은 단순 저장소 — 표 형태의 데이터(목록, 조회, 수정)를 다루기 어려워 만들 수 있는 시스템이 좁아집니다.
