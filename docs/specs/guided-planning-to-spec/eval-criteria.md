# agent 대화 품질 eval 판정 기준

[spec.md](spec.md)의 "agent 대화 품질" 기준 세 개를 어떻게 채점하는지 적습니다. 사례는 [eval-cases.jsonl](eval-cases.jsonl)에 있고, `split`이 `test`인 20개(재료 10, 직접 적은 아이디어 10)가 최종 판정용입니다. `train` 8개는 프롬프트를 다듬는 데만 씁니다. 두 묶음은 겹치지 않습니다.

실행기는 앱의 실제 진입점(`handleAgentRequest`)을 그대로 호출합니다. 한 사례는 다음 순서로 진행합니다.

1. (재료 사례만) 고른 재료로 아이디어 추천을 받습니다.
2. 2단계: agent의 첫 질문 → 사례에 적힌 사용자 답 2개 → "잘 모르겠어요, 예시를 보여주세요" → "이 질문은 나중에" 순서로 대화합니다.
3. 방향을 확정하고 3단계: agent의 첫 결과 제안 → "괜찮아요, 이대로 갈게요" → "그런데 기록도 남기고 알림도 여러 개 받고 싶어요"(결과를 늘리려는 요구)로 대화합니다.

## 1. 아이디어 추천 (재료 사례만)

판정: 추천된 3개 아이디어 각각이 **고른 재료만으로 설명되는지** 봅니다. 재료 전체 목록(PRODUCT.md)에서 고르지 않은 재료가 있어야 동작하는 아이디어(예: 메일을 고르지 않았는데 메일로 보냄, 사진 읽기를 고르지 않았는데 사진을 분석함)가 하나라도 있으면 그 사례는 실패입니다. 재료 목록에 없는 일반 기능(화면 보기, 간단한 계산)은 문제 삼지 않습니다. 아이디어 문장에 그 기능이 명시적으로 드러날 때만 실패로 보고, "필요할 수 있다"는 추측만으로는 실패로 보지 않습니다(심사 지시 v2, 2026-11-19 사용자 승인). 채점은 claude CLI가 맡고, 아이디어마다 참/거짓과 이유를 남깁니다.
통과 목표: 재료 사례를 반복해서 합산한 통과율 80% 이상(2026-11-19 사용자 승인으로 "10개 중 9개"에서 조정).

## 2. 한 번에 하나씩 묻기 (2·3단계 응답 전체)

판정: agent의 응답 하나가 **질문을 최대 하나** 담으면 통과입니다. 질문은 `?`로 끝나거나 "나요/까요/인가요/있나요" 같은 의문형으로 끝나는 문장이며, 응답 안의 질문 문장 개수를 코드로 셉니다. 2단계 5개 응답과 3단계 3개 응답, 사례당 8개를 모두 셉니다.
통과 목표: 전체 응답의 90% 이상.

## 3. 첫 Spec 크기 (20개 사례)

3단계 대화가 끝난 시점의 첫 Spec(`result`, `scope`, `verification`, `notNow`)을 봅니다. 다음 셋을 모두 만족해야 통과입니다.

- 네 항목 채움(코드): `result`가 비어 있지 않고, `scope`와 `verification`이 각각 1개 이상, `notNow`가 비어 있지 않습니다.
- 결과가 하나뿐(claude CLI): `result`가 사용자가 얻는 서로 다른 결과를 둘 이상 나열하지 않습니다. "그리고/및"으로 이어진 무관한 두 결과, 마지막 대화에서 사용자가 요구한 추가 결과(기록, 여러 알림)가 `result`나 `scope`에 섞여 들어오면 실패입니다.
- 한 번에 써 볼 크기(claude CLI): `scope`가 5개 이하이고, 계정·로그인·결제·여러 화면·여러 플랫폼이 필요하지 않으며, `verification`이 사용자가 직접 해 보고 확인할 수 있는 행동입니다. 알림이나 메일처럼 시간이 지나 도착하는 결과를 "다음 날 아침 7시에 알림이 오는지"처럼 구체적인 시점과 함께 확인하는 방법은 허용합니다. 앱 밖의 현실 활동, "잘 되는지/정확한지/제대로 나오는지" 같이 무엇을 보면 되는지 알 수 없는 막연한 표현, scope에 없는 기능을 확인하는 방법은 실패입니다(심사 지시 v2, 2026-11-19 사용자 승인).

통과 목표: 20개 사례를 반복해서 합산한 통과율 60% 이상(2026-11-19 사용자 승인으로 "20개 중 18개"에서 조정).
