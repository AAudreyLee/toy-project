# 첫 Spec을 코드로 만들어 내 GitHub에 올리고 Vercel에 배포하기

3단계에서 확정한 첫 Spec을 agent가 코드로 만들어 사용자 본인의 GitHub 새 비공개 저장소에 올리고, 사용자 본인의 Vercel에 배포합니다. 사용자는 배포 주소에서 자기가 만든 시스템을 직접 써 보고 Spec의 확인 방법으로 확인합니다. 핵심 루프의 4단계(구현)와 5단계(배포)를 한 번에 다루는 결과이며, 외부 계정이나 키가 더 필요 없는 시스템만 만듭니다.

## Linked sources

- [guided-planning-to-spec](../guided-planning-to-spec/spec.md) — 앞선 결과(1~3단계, 병합됨)입니다. 로드맵, 대화·문서 화면의 구성, "다시 확인" 규칙, 브라우저 보존 방식은 그 spec과 구현을 따릅니다. 이 결과가 잠겨 있던 4·5단계를 엽니다.
- [docs/decisions/credential-storage.md](../../decisions/credential-storage.md) — GitHub는 OAuth로, Vercel은 사용자가 발급한 토큰을 직접 입력해 연결합니다. 받은 권한은 브라우저에만 보관하며 서버는 저장하지 않습니다.
- [docs/decisions/deployment-ownership.md](../../decisions/deployment-ownership.md) — 코드 저장소와 배포는 사용자 본인의 계정이고, 첫 범위에서 agent가 자동으로 배포하는 대상은 Vercel뿐입니다.
- [docs/decisions/llm-usage-billing.md](../../decisions/llm-usage-billing.md) — 코드를 만드는 agent의 LLM 호출은 사용자 본인의 키(현재 Azure OpenAI)로 합니다.
- [docs/decisions/ui-composition.md](../../decisions/ui-composition.md) — 일반 UI는 shadcn 구성과 현재 preset 토큰을 씁니다.

## User-visible outcomes

- 사용자는 "GitHub로 연결" 버튼으로 GitHub를 승인하고, Vercel에서 발급한 토큰을 붙여 넣어 Vercel을 연결합니다.
- 3단계를 확정하고 두 계정을 연결하면, 사용자가 확인한 저장소 이름으로 agent가 코드를 만들어 새 비공개 저장소에 올리고 Vercel에 배포합니다.
- 진행되는 동안 지금 어느 일을 하는지(코드 만드는 중, 저장소 만드는 중, 올리는 중, 배포 중, 확인 중)가 보입니다.
- 배포가 끝나면 배포 주소와 Spec의 확인 방법이 함께 보이고, 사용자는 주소를 열어 직접 확인합니다.
- 외부 계정이나 키가 필요한 Spec(저장, 알림, 키가 필요한 공개 데이터)은 이유를 안내하고 구현을 시작하지 않습니다.
- 실패하면 원인을 알리고 다시 시도할 수 있습니다.

## Scope

포함:

- GitHub OAuth 연결, Vercel 토큰 입력과 확인, 연결 상태 보기, 연결 해제와 다시 연결
- 4단계 구현: 저장소 이름 제안과 확인, 지원 범위 판정, 코드 생성, 새 비공개 저장소 생성과 업로드
- 5단계 배포: Vercel 프로젝트 생성과 배포, 배포 주소 확인, Spec 확인 방법 안내
- 진행 상황 표시, 실패 안내와 다시 시도
- 로드맵의 4·5단계가 잠김에서 열리고, 구현 이후 앞 단계를 고치면 "다시 확인"으로 표시
- 구현·배포 결과(저장소 주소, 배포 주소)와 연결 상태를 이 브라우저에 보존

제외는 [Off-limits](#off-limits)를 봅니다.

## Acceptance criteria

연결

- 3단계가 완료되면 로드맵 4·5단계가 잠김에서 풀려 눌러서 들어갈 수 있습니다. 3단계가 완료되지 않았으면 계속 잠겨 있고 "먼저 Spec을 확정해 주세요"가 보입니다.
- "GitHub로 연결"을 누르면 GitHub 승인 화면으로 가고, 승인하면 돌아와 "GitHub 연결됨"과 사용자 이름이 보입니다.
- Vercel은 토큰 입력칸에 Vercel에서 발급한 토큰을 붙여 넣고 "연결"을 누르면, 서비스가 그 토큰으로 Vercel에 요청해 확인한 뒤 "Vercel 연결됨"과 사용자 이름이 보입니다. 입력칸이 비었거나 토큰이 거부되면 "토큰을 확인하지 못했어요"가 뜨고 연결되지 않습니다. "토큰은 어디서 받나요?"를 누르면 발급 방법(Vercel 계정 설정의 토큰 메뉴, 계정 또는 팀 범위)이 보입니다.
- GitHub 승인을 취소하거나 연결에 실패하면 원인을 알리는 안내가 뜨고 연결되지 않은 상태로 남으며 다시 시도할 수 있습니다.
- GitHub가 준 접근 권한과 사용자가 붙여 넣은 Vercel 토큰은 이 브라우저에만 보관됩니다. 서비스 서버가 저장하거나 로그에 남기지 않습니다. — [credential-storage](../../decisions/credential-storage.md)
- 연결된 계정은 "연결 해제"로 끊을 수 있고, 끊으면 브라우저에서 권한이 지워집니다. 구현·배포 진행 중에 권한이나 토큰이 만료되거나 거부되면 원인을 알리고 다시 연결하게 합니다. 이미 만든 결과는 사라지지 않습니다.
- 두 계정이 모두 연결되기 전에는 "구현 시작"을 누를 수 없고, 무엇이 아직 연결되지 않았는지 보입니다.

지원 범위 판정

- 확정된 첫 Spec이 외부 계정이나 키가 더 필요한 시스템(데이터를 저장해 두고 다시 보여 주기, 메일·메신저 발송, 키가 필요한 공개 데이터, 예약 실행)이면 "이번엔 만들 수 없어요"와 이유, 그리고 Spec을 어떻게 고치면 되는지가 보이고 구현이 시작되지 않습니다. 사용자는 3단계로 돌아가 Spec을 고칠 수 있습니다.
- 키가 필요 없는 시스템(화면에 입력하고 결과를 보여 주는 것, 키가 필요 없는 공개 데이터)이면 구현을 시작할 수 있습니다.

구현과 배포

- "구현 시작"을 누르면 agent가 저장소 이름(프로젝트 이름 기반)을 제안하고, 사용자가 이름을 확인하거나 고친 뒤 "만들고 올리기"를 눌러야 저장소가 만들어집니다. 누르기 전에는 사용자의 GitHub 계정에 아무것도 생기지 않습니다.
- 저장소는 새 비공개 저장소로 만들어집니다. 같은 이름의 저장소가 이미 있으면 덮어쓰지 않고 이름을 바꾸라고 안내합니다. 기존 저장소에는 올리지 않습니다. — [deployment-ownership](../../decisions/deployment-ownership.md)
- 진행 중에는 현재 하는 일이 단계별로 보이고, 끝난 일은 표시됩니다. 진행 중에도 화면을 떠났다가 돌아오면 지금까지의 진행 상태가 이어서 보입니다.
- 코드 생성에는 사용자 본인의 키(Azure OpenAI)가 쓰입니다. 운영자 키로 대신하지 않습니다. — [llm-usage-billing](../../decisions/llm-usage-billing.md)
- Vercel이 새로 만든 저장소를 볼 수 없어 프로젝트를 연결하지 못하면(사용자의 GitHub에 Vercel GitHub 앱이 없거나 이 저장소 접근이 허용되지 않은 경우), 원인과 해결 방법(Vercel GitHub 앱을 설치하고 이 저장소 접근을 허용)을 알리고, 해결한 뒤 "다시 시도"로 이어서 배포합니다. 이미 만든 저장소는 그대로 남습니다.
- 배포가 성공하면 서비스가 배포 주소에 실제로 요청해 응답을 확인하고, 응답이 정상일 때만 "배포 완료"와 배포 주소 링크, 저장소 링크, Spec의 확인 방법이 보입니다.
- 배포 빌드가 실패하면 agent가 실패 내용을 읽고 코드를 고쳐 다시 올리는 시도를 최대 2번 합니다. 그래도 실패하면 원인을 알리고 "다시 시도"를 누를 수 있으며, 이미 만든 저장소는 그대로 남습니다.
- 코드 생성이나 저장소·Vercel 호출이 키 문제 외의 이유로 실패하면 어느 일에서 실패했는지 알리고 같은 일을 다시 시도할 수 있게 합니다.

로드맵과 다시 확인

- 구현이 완료된 뒤 1~3단계를 고쳐 내용이 바뀌면, 4·5단계는 결과를 유지한 채 "다시 확인"으로 표시됩니다. "다시 확인"인 4단계에 들어가면 무엇이 바뀌었는지가 보이고, 이 결과에서는 다시 만들기를 제공하지 않습니다(안내만 보입니다).
- 4·5단계 화면에서도 로드맵과 "지금 할 일"이 보입니다.

보존

- 새로고침하거나 브라우저를 닫았다가 다시 열어도 연결 상태, 저장소 주소, 배포 주소, 4·5단계 상태가 이어집니다. 진행 중이던 구현은 이어지지 않고, 중단된 지점을 알리며 다시 시작할 수 있습니다.

화면

- 화면 폭 390px, 768px, 데스크톱에서 모든 화면의 내용과 버튼이 잘리거나 가려지지 않습니다.
- 모든 화면 문구는 한국어입니다.

agent 구현 품질(실행마다 결과가 달라 eval로 증명)

- 평가 사례: 구현 단계에서 이 폴더에 평가 사례 파일을 만듭니다. [guided-planning-to-spec의 평가 사례](../guided-planning-to-spec/eval-cases.jsonl)에서 나온 첫 Spec 20개와, 지원 범위 밖 Spec 10개(저장, 메일·메신저 발송, 키가 필요한 데이터, 예약 실행을 요구하는 Spec)로 이루어진 30개 사례를 쓰고, 프롬프트를 다듬는 데 쓴 사례와 겹치지 않게 둡니다. 판정 기준은 사례 파일에 함께 적습니다.
- 지원 범위 판정: 지원 범위 안 Spec은 구현으로 통과시키고 범위 밖 Spec은 막는 판정이 전체 사례의 90% 이상에서 맞아야 합니다.
- 생성한 코드가 빌드됨: 지원 범위 안 Spec 20개로 코드를 만들어 빌드했을 때, 반복해서 합산한 통과율이 70% 이상이어야 합니다. 자동 수정 시도가 있으면 최종 결과로 판정합니다.

## Constraints and rationale

- GitHub는 OAuth로, Vercel은 사용자가 발급한 토큰으로 연결하고, 받은 권한은 브라우저에만 보관하며 서버는 저장하지 않습니다. — [credential-storage](../../decisions/credential-storage.md). 서버 저장은 로그인과 서버 저장소를 요구해 이 결과의 범위를 넘고, Vercel OAuth는 프로젝트·배포 API 권한이 비공개 베타여서 지금 쓸 수 없습니다.
- 코드 저장소와 배포는 사용자 본인의 계정이고, 자동 배포 대상은 Vercel뿐입니다. — [deployment-ownership](../../decisions/deployment-ownership.md)
- 코드 생성의 LLM 호출은 사용자 본인 키로 합니다. — [llm-usage-billing](../../decisions/llm-usage-billing.md)
- 저장소는 새 비공개 저장소만 만듭니다. — 기존 코드를 덮어쓰거나 충돌할 위험이 없고, 사용자가 누르기 전에는 계정에 아무것도 생기지 않게 하려는 선택입니다.
- 외부 계정이나 키가 더 필요 없는 시스템만 만듭니다. — 사용자가 한 번에 만들고 배포 주소에서 직접 확인할 수 있는 크기로 정했고, 저장·알림·키가 필요한 재료는 다음 결과로 미룹니다.
- 4·5단계를 한 결과로 묶습니다. — 코드 생성, 저장소 업로드, 배포 확인이 서로 얽혀 있어 한쪽만으로는 사용자가 확인할 결과가 없습니다.
- 현재 단계와 다음 행동이 항상 보여야 합니다. — PRODUCT.md 경험 원칙.

## Assumptions

다음은 agent가 정한 기본값입니다. 사용자가 언제든 바꿀 수 있습니다.

- 만들어지는 시스템의 기술은 Next.js 하나로 고정합니다. 사용한 기술은 결과 화면에 알려 주고, 선택지는 주지 않습니다. 배포 대상이 Vercel이고 외부 계정이 필요 없는 범위여서 선택지를 둘 이유가 약합니다.
- 저장소 이름은 프로젝트 이름을 소문자와 하이픈으로 바꿔 제안합니다.
- "다시 열어도 남는 기록"은 사용자의 브라우저 저장소(localStorage)에 두는 것으로 만들 수 있다고 봅니다. 다른 기기나 다른 사람과 데이터를 공유해야 하는 서버 저장은 만들 수 없는 것으로 막습니다. 서버 저장은 다음 결과에서 따로 다룹니다.
- 빌드가 실패하면 자동으로 고쳐 다시 올리는 시도는 최대 2번입니다.
- 배포 주소가 "정상"이라는 판정은 배포 주소가 오류 없이 화면을 돌려주는 것입니다.
- 4·5단계 화면은 1~3단계 화면(로드맵, 지금 할 일, 카드 구성)과 같은 구성을 씁니다. 이 결과를 위한 prototype은 만들지 않았고, 구현 뒤 화면을 보고 조정할 수 있습니다.
- GitHub OAuth 권한은 구현에 필요한 최소한(저장소 생성과 업로드)으로 하고, 구체적인 항목은 구현할 때 공식 문서로 정합니다. Vercel 토큰은 사용자가 계정(또는 팀) 범위로 발급하고, 서비스는 프로젝트 생성과 배포 조회에만 씁니다.

## Off-limits

- 로그인과 계정 — OAuth는 GitHub 연결에만 쓰며, 이 서비스 자체의 로그인이 아닙니다. 서비스 로그인과 여러 기기 동기화는 이후 결과에서 다룹니다.
- 서버에 접근 권한 저장 — [credential-storage](../../decisions/credential-storage.md)가 금지합니다.
- Vercel OAuth 연결 — Vercel의 프로젝트·배포 API 권한이 비공개 베타여서 지금은 토큰 직접 입력으로 합니다. Deferred를 봅니다.
- 기존 GitHub 저장소 선택과 공개 저장소 — 새 비공개 저장소만 만듭니다.
- 외부 계정이나 키가 필요한 시스템(저장소·데이터베이스, 메일·메신저 발송, 키가 필요한 공개 데이터, 예약 실행) — 다음 결과로 미룹니다.
- 기술 자문과 기술 선택지(효율·대중성 순 추천) — 기술을 하나로 고정합니다.
- Vercel 외 배포 대상(내부 서버 등) — [deployment-ownership](../../decisions/deployment-ownership.md)가 이후로 미룹니다.
- 사용자 도메인 연결, 환경 변수 설정, 롤백과 재배포 관리 — 이 결과는 첫 배포만 다룹니다.
- 구현 뒤 Spec이 바뀌었을 때 다시 구현하기, 다음 기능 반복 — 이 결과는 "다시 확인" 표시와 안내까지만 합니다.
- 관제 화면, 에러 기록과 운영자 알림, 개발 히스토리와 개발 일지 export — 이후 결과로 미룹니다.

## Deferred

- 외부 계정이나 키가 필요한 재료(저장, 알림, 키가 필요한 공개 데이터) 지원 — 이 결과가 출시되어 사용자가 실제로 만들려는 Spec이 어떤 재료를 많이 요구하는지 보인 뒤 다시 엽니다. 임시 동작: 해당 Spec은 구현을 막고 이유를 안내합니다.
- 기술 자문과 기술 선택지 — 지원 범위가 넓어져 선택지가 의미 있을 때 다시 엽니다. 임시 동작: Next.js 하나로 고정합니다.
- 구현 뒤 Spec이 바뀔 때의 다시 구현과 다음 기능 반복 — 핵심 루프의 마지막 줄(Spec 정리 후 다음 기능)을 shape할 때 다시 엽니다. 임시 동작: "다시 확인" 표시와 안내만 보입니다.
- Vercel OAuth 연결 — Vercel이 프로젝트 생성과 배포를 다루는 API 권한(Permissions)을 비공개 베타에서 일반에 공개하면 다시 엽니다. 임시 동작: 사용자가 Vercel 토큰을 직접 붙여 넣습니다.
- 접근 권한과 진행 상황의 서버 보관 — 로그인이 들어오는 결과를 shape할 때 다시 엽니다. 임시 동작: 브라우저에만 저장합니다.

## Remaining risks

- Vercel 토큰은 사용자가 직접 발급해 붙여 넣어야 하고, 계정 또는 팀 범위의 강한 권한입니다. 비개발자가 토큰 발급 단계에서 이탈하거나 권한이 과하다고 느낄 수 있습니다. 발급 안내의 질이 연결 경험을 좌우합니다.
- 사용자 GitHub에 Vercel GitHub 앱이 없거나 새 저장소 접근이 허용되지 않으면 배포가 막힙니다. 이를 안내와 다시 시도로 풀게 했지만, 이 단계에서도 이탈할 수 있습니다. Vercel이 새로 만든 저장소를 연결하는 흐름은 공식 문서로만 확인했고 직접 실행해 보지 않았습니다.
- 사용자 계정에 저장소 생성 권한을 요구하므로, 승인 화면에서 비개발자가 이탈하거나 권한을 과하게 느낄 수 있습니다.
- 브라우저 데이터를 지우면 연결과 결과 주소가 사라집니다. 저장소와 배포는 사용자 계정에 남아 있습니다.
- agent가 만든 코드는 서비스가 직접 실행해 보지 못하고 Vercel 빌드로만 확인합니다. 빌드는 통과해도 Spec의 확인 방법을 만족하지 못할 수 있습니다.
- agent 구현 품질은 모델과 프롬프트에 따라 흔들립니다. 앞선 결과에서 같은 종류의 eval 목표를 처음 값으로 달성하지 못했던 경험이 있어, 위 목표(70%, 90%)에 못 미치면 확정 전에 목표나 방법을 다시 정해야 할 수 있습니다.

## Setup before implementation

- GitHub OAuth 앱 등록 — 사용자가 GitHub로 연결하는 흐름에 필요합니다. 완료 조건: 테스트용 GitHub 계정으로 앱 밖에서 승인 절차를 거쳐 접근 권한을 받고, 그 권한으로 GitHub API에서 사용자 정보 조회와 새 비공개 저장소 생성이 성공하는 것.
- Vercel 테스트용 계정과 토큰 — 사용자가 Vercel을 연결하는 흐름과 배포에 필요합니다. 테스트용 GitHub 계정에는 Vercel GitHub 앱이 설치되어 있어야 합니다. 완료 조건: 그 토큰으로 앱 밖에서 Vercel API를 호출해 사용자 정보 조회, 새 프로젝트 생성(GitHub 저장소 연결 포함), 배포 조회가 성공하는 것.
- GitHub OAuth 콜백 주소 등록 — GitHub가 승인 뒤 돌려보낼 주소가 필요합니다. 완료 조건: 개발 환경 콜백 주소가 GitHub OAuth 앱에 등록되어 있고, 등록된 주소로 승인 응답이 도착하는 것을 앱 밖에서 확인하는 것.
- 구현자가 쓸 테스트용 Azure OpenAI 연결 정보 — 앞선 결과에서 준비한 것(환경 변수 `AZURE_OPENAI_API_KEY`, `AZURE_OPENAI_ENDPOINT`, `AZURE_OPENAI_DEPLOYMENT`)을 그대로 씁니다. 완료 조건: 그 정보로 앱 밖에서 배포를 직접 호출해 정상 응답을 받는 것.
