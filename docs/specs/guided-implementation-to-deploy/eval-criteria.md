# agent 구현 품질 eval 판정 기준

[spec.md](spec.md)의 "agent 구현 품질" 기준 두 개를 어떻게 채점하는지 적습니다. 사례는 [eval-cases.jsonl](eval-cases.jsonl)에 있고, `split`이 `test`인 30개(만들 수 있는 20, 막아야 하는 10)가 최종 판정용, `train` 17개가 프롬프트를 다듬는 데 쓴 사례입니다. 두 묶음은 겹치지 않습니다. 사례의 첫 Spec은 [guided-planning-to-spec](../guided-planning-to-spec/spec.md) eval에서 앱이 실제로 만든 것이고, `label`과 `reason`은 사람이 판단해 적었습니다.

실행기는 앱의 실제 진입점(`handleDeliveryRequest`)을 Azure OpenAI 배포로 호출합니다. 판정은 코드로만 하며 모델이나 구독을 쓰지 않습니다. 졸업한 회귀 묶음은 `.claude/hillclimb/regression/`에 있습니다.

## 지원 범위 판정

- 만들 수 있다고 라벨된 Spec은 통과시키고(`supported: true`), 막아야 한다고 라벨된 Spec은 막아야(`supported: false`) 맞습니다.
- "만들 수 있다"의 기준: 추가 계정이나 키 없이 만들 수 있는 것입니다. 한 화면에서 입력·선택·계산·목록, 같은 브라우저에서 다시 열어도 남는 기록(브라우저 저장소)이 포함됩니다. "막아야 한다"의 기준: 다른 기기·다른 사람과 데이터를 공유하는 것, 메일·메신저 등 알림과 예약 실행, 로그인, 키가 필요한 외부 서비스(AI, 사진 분석, 공공 데이터).
- 통과 목표: 최종 판정용 30개를 반복해서 합산한 정확도 90% 이상. (2026-11-19 측정: baseline 35%, 최종 92%, 표본 잡음 약 ±13점.)

## 생성한 코드의 빌드

- 만들 수 있다고 라벨된 Spec(최종 판정용 20개)으로 코드를 만들어 `next build`를 돌립니다. 실패하면 앱과 같은 방식으로 빌드 로그를 주고 최대 2번 고쳐 다시 빌드하고, 최종 결과로 판정합니다.
- 통과 목표: 반복해서 합산한 통과율 70% 이상. (2026-11-19 측정: baseline 91%, 최종 92%, 첫 빌드만으로는 59~62%, 표본 잡음 약 ±16점.) 코드 생성 자체가 규칙에 맞지 않아 끝내 실패한 시도는 빌드 결과가 없어 점수에서 빼고 따로 기록합니다(최종 3건, 포함하면 34/40, 85%).
