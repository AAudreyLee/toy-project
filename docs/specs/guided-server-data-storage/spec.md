# 만들어진 시스템이 입력한 데이터를 내 데이터베이스에 저장하기

첫 Spec이 "데이터를 저장해 두고 다시 보여 주는" 시스템이면, agent가 사용자 본인의 Vercel 팀에 Neon(Postgres) 데이터베이스를 새로 만들고 그 데이터를 서버에 저장하는 시스템으로 코드를 만들어 배포합니다. 배포된 시스템은 다른 기기와 다른 사람이 같은 데이터를 보고 쓸 수 있습니다. 로그인이 필요한 사용자별 비공개 데이터는 다루지 않습니다.

## User-visible outcomes

- 첫 Spec이 "데이터를 서버에 저장해야 하는 시스템"이면, 4단계에서 "데이터를 저장할 데이터베이스가 필요해요"라는 안내가 보입니다. 저장이 필요 없거나 같은 브라우저에 남는 기록이면 충분한 시스템에서는 데이터베이스를 언급하지 않습니다.
- 사용자의 Vercel 팀에 Neon 연동이 아직 없으면, 서비스가 그 사실과 Vercel 대시보드에서 한 번 설치하는 방법(약관 동의 포함)을 안내하고, 설치한 뒤 "다시 확인"으로 이어갑니다. 이미 설치되어 있으면 이 단계가 보이지 않습니다.
- 구현을 시작하면 저장소와 배포뿐 아니라 사용자의 Vercel 팀에 새 데이터베이스가 만들어지고 배포 프로젝트에 연결되어, 시스템이 그 데이터베이스에 데이터를 저장합니다.
- 배포 주소에서 데이터를 입력하면 다른 브라우저나 다른 기기에서 같은 주소를 열어도 그 데이터가 보입니다.
- 진행 중에는 "데이터베이스 만드는 중"이 다른 단계와 함께 보입니다.
- 저장이 필요하더라도 로그인이나 사용자별 비공개 데이터, 알림, 예약 실행, 키가 필요한 외부 서비스가 필요한 Spec은 이전처럼 이유를 안내하고 구현을 시작하지 않습니다.
- 실패하면 원인을 알리고 다시 시도할 수 있으며, 이미 만든 데이터베이스는 다시 만들지 않고 이어서 씁니다.

## Scope

포함:

- 지원 범위 판정의 세 갈래 구분: 계정 없이 만들 수 있음(브라우저 저장소 포함), 서버 저장이 필요해 데이터베이스까지 만들 수 있음, 만들 수 없음
- 사용자 Vercel 팀의 Neon 연동 설치 여부 확인과 설치 안내(서버 저장이 필요한 Spec일 때만)
- 새 데이터베이스 생성, 데이터를 담을 표 생성, 배포 프로젝트에 연결해 접속 정보를 환경 변수로 넣기
- 서버에 데이터를 저장하고 읽는 시스템 코드 생성과 배포
- 진행 표시 확장, 실패 안내와 다시 시도, 데이터베이스 연결 결과의 브라우저 보존
- 공유 데이터 안내(주소를 아는 누구나 데이터를 보고 고칠 수 있음)

제외는 [Off-limits](#off-limits)를 봅니다.

## Acceptance criteria

지원 범위 판정

- 확정된 첫 Spec이 공유 데이터를 서버에 저장해야 하는 시스템(예: 모두가 같이 쓰는 공지·할 일 목록, 설문 수집)이면 "데이터베이스가 필요해요"와 함께 구현을 시작할 수 있습니다.
- 로그인·사용자별 비공개 데이터, 메일·메신저 발송, 예약 실행, 키가 필요한 외부 서비스가 필요한 Spec은 이유와 Spec을 어떻게 고치면 되는지가 보이고 구현이 시작되지 않습니다.
- 데이터 저장이 같은 브라우저에서만 남으면 충분한 Spec은 이전처럼 데이터베이스 없이 만들고 Neon을 묻지 않습니다.

Neon 준비

- 서버 저장이 필요한 Spec은 GitHub와 Vercel이 모두 연결되기 전에는 "구현 시작"을 누를 수 없고, 무엇이 아직 연결되지 않았는지 보입니다. 이 결과는 새 계정이나 토큰을 요구하지 않습니다. — [credential-storage](../../decisions/credential-storage.md)
- 서비스가 사용자의 Vercel 토큰으로 Neon 연동이 설치되어 있는지 확인합니다. 설치되어 있지 않으면 설치 방법과 "다시 확인" 버튼이 보이고, 설치된 뒤 다시 확인하면 구현을 시작할 수 있습니다. 확인하지 못하면 원인을 알리고 다시 시도할 수 있습니다.
- Neon이 준비되지 않았거나(연동 미설치, 토큰 거부, 결제 수단 없음 등) 데이터베이스를 만들지 못하면, 서버 저장이 필요한 시스템은 구현을 중단하고 원인만 안내합니다. 브라우저 저장소로 바꿔 만들거나 데이터베이스 없이 일부만 만들어 배포하지 않습니다.

구현과 배포

- "구현 시작" 단계에서 저장소 이름 확인과 함께 "내 Vercel 팀에 새 데이터베이스가 만들어져요"와 "주소를 아는 누구나 이 데이터를 보고 고칠 수 있어요"가 보입니다. 사용자가 "만들고 올리기"를 누르기 전에는 GitHub, Vercel 어디에도 아무것도 생기지 않습니다.
- 데이터베이스는 사용자의 Vercel 팀에 새로 만들어지고, 기존 데이터베이스에는 아무것도 하지 않습니다. 같은 이름이 이미 있어도 덮어쓰지 않습니다. — [deployment-ownership](../../decisions/deployment-ownership.md)
- 배포가 시작되기 전에 접속 정보가 Vercel 프로젝트에 들어가 있어서, 배포된 시스템이 처음부터 데이터를 저장하고 읽을 수 있습니다.
- 데이터베이스 접속 정보(비밀 키, 비밀번호)는 생성된 저장소의 코드에도, 브라우저로 내려가는 화면 코드에도, 서비스 화면과 로그에도 나타나지 않습니다. 접속 정보는 사용자의 Vercel 프로젝트 환경 변수에만 있습니다. — [server-data-storage](../../decisions/server-data-storage.md)
- 배포가 끝나면 배포 주소에서 데이터를 입력해 저장하고, 새로고침하거나 다른 브라우저로 같은 주소를 열어도 그 데이터가 보입니다. 이 확인 방법이 Spec의 확인 방법과 함께 안내됩니다.
- 데이터베이스가 준비되기까지 시간이 걸리면 "데이터베이스 만드는 중"이 보이고, 정해진 시간 안에 준비되지 않으면 원인과 다시 시도 방법을 알립니다.
- 무료 플랜의 데이터베이스 수 한도에 걸리거나 결제 수단이 필요하다는 응답을 받으면, 원인과 해결 방법(기존 데이터베이스 정리나 Vercel 결제 수단 등록)을 알리고 다시 시도할 수 있게 합니다. 이미 만든 저장소와 Vercel 프로젝트는 그대로 남습니다.
- 다시 시도하면 이미 만든 데이터베이스는 다시 만들지 않고 이어서 씁니다.
- 빌드 실패 시 자동 수정 최대 2번, 같은 이유 실패 시 다시 시도 같은 앞선 결과의 동작은 서버 저장이 있는 시스템에서도 그대로입니다.

로드맵과 보존

- 구현이 완료된 뒤 1~3단계를 고쳐 내용이 바뀌면 4·5단계는 앞선 결과와 같이 "다시 확인"으로 표시되며, 이 결과에서도 다시 만들기를 제공하지 않습니다.
- 새로고침하거나 브라우저를 닫았다가 다시 열어도 데이터베이스 연결 결과(이름)가 이어집니다. 접속 정보는 보존하지 않습니다. 진행 중이던 구현은 이어지지 않고 중단된 지점을 알리며 다시 시작할 수 있습니다.

화면

- 화면 폭 390px, 768px, 데스크톱에서 모든 화면의 내용과 버튼이 잘리거나 가려지지 않습니다.
- 모든 화면 문구는 한국어입니다.

agent 구현 품질(실행마다 결과가 달라 eval로 증명)

- 평가 사례: 구현 단계에서 이 폴더에 평가 사례 파일을 만듭니다. 앞선 결과의 [사례](../guided-implementation-to-deploy/eval-cases.jsonl) 중 만들 수 있는 첫 Spec(브라우저 저장소로 충분한 것 포함)과 막아야 하는 Spec, 그리고 이 결과에서 새로 만드는 공유 데이터 서버 저장 Spec과 서버 저장이 필요하지만 로그인 등으로 막아야 하는 Spec으로 이루어진 사례를 쓰고, 프롬프트를 다듬는 데 쓴 사례와 겹치지 않게 둡니다. 새 사례는 각각 10개 이상이고, 판정 기준은 사례 파일에 함께 적습니다.
- 지원 범위 세 갈래 판정: 사례마다 정해 둔 갈래(데이터베이스 없이 만들 수 있음, 서버 저장이 필요함, 막아야 함)로 판정이 맞는 비율이 전체 사례에서 85% 이상이어야 합니다. 앞선 결과의 "지원 범위 판정" 회귀 사례는 이 변경 뒤에도 이전 수준(90% 이상)을 유지해야 합니다.
- 서버 저장 시스템 코드가 빌드됨: 서버 저장이 필요한 Spec 15개로 코드를 만들어 빌드했을 때, 반복해서 합산한 통과율이 70% 이상이어야 합니다. 자동 수정 시도가 있으면 최종 결과로 판정합니다.
- 비밀 키 노출 없음: 생성된 코드에 비밀 키 값이나 비밀 키를 읽는 코드가 브라우저로 내려가는 파일에 들어 있지 않아야 합니다. 이는 코드로 검사하는 규칙이며, 위반하면 빌드 통과로 세지 않습니다.

## Constraints and rationale

- 데이터는 사용자 본인의 Vercel 팀에 Neon 데이터베이스로, 시스템당 하나 새로 둡니다. — [server-data-storage](../../decisions/server-data-storage.md). 저장소·Vercel 프로젝트·데이터베이스가 1:1:1이라 소유와 삭제 경계가 분명하고, 이미 연결하는 Vercel 토큰 하나로 되어 사용자가 넣을 값이 늘지 않습니다.
- 서버 저장은 로그인 없는 공유 데이터만 다룹니다. 사용자별 권한 규칙과 생성 코드의 보안 검증 부담이 한 번에 만들 결과에 비해 크기 때문입니다. — [server-data-storage](../../decisions/server-data-storage.md)
- 생성된 서버 코드만 비밀 키로 데이터베이스에 접근하고 브라우저는 직접 붙지 않습니다. 로그인이 없으므로 브라우저에 접근 권한을 내려주면 누구나 데이터를 지울 수 있기 때문입니다.
- 서버 저장이 필요 없는 시스템에는 Neon 설치를 요구하지 않습니다. 설치 단계를 필요한 경우에만 겪게 하려는 선택입니다.
- 지원 범위 판정을 두 갈래에서 세 갈래로 넓히고, 서버 저장이 필요하다고 판정할 때만 Neon 준비를 요구합니다.
- 현재 단계와 다음 행동이 항상 보여야 합니다. — PRODUCT.md 경험 원칙.

## Assumptions

다음은 agent가 정한 기본값입니다. 사용자가 언제든 바꿀 수 있습니다.

- Neon 연동의 첫 설치(약관 동의)는 사용자가 Vercel 대시보드에서 직접 합니다. 이 설치를 API만으로 대신할 수 있는지는 확인하지 못했고, 구현 전에 실제 호출로 확인합니다. 대신할 수 있으면 이 안내 단계를 없앨 수 있습니다.
- 데이터베이스 이름은 저장소 이름을 기반으로 하고, 지역과 플랜은 구현할 때 공식 문서로 정합니다(무료 플랜 우선).
- 데이터를 담을 표 구조는 첫 Spec에서 agent가 정하고, 사용자는 SQL을 보지 않습니다. 표 구조를 사용자가 확인하거나 고치는 단계는 두지 않습니다.
- 표를 어떻게 만들지(데이터베이스에 직접 SQL을 실행하는 방법과 그 접속 정보를 서비스가 어떻게 얻는지), 데이터베이스 준비를 기다리는 시간 한도, 무료 플랜의 데이터베이스 수 한도는 구현 전에 실제 호출로 확인합니다. 문서만으로는 확인하지 못했습니다.
- 서버 저장이 있는 시스템의 접근 방식(어떤 데이터베이스 클라이언트를 쓰는지 등)은 구현할 때 공식 문서와 설치된 버전에 맞춰 정합니다. 앞선 결과가 만드는 코드의 허용 범위(외부 패키지, 환경 변수, 서버 코드 파일)는 이 결과에 필요한 만큼 넓히며, 넓히는 범위는 서버 저장 시스템에만 적용합니다.
- 4·5단계 화면은 앞선 결과의 구성을 쓰고, 이 결과를 위한 prototype은 만들지 않았습니다. 구현 뒤 화면을 보고 조정할 수 있습니다.
- 앞선 결과에서 받는 Vercel 토큰의 범위(계정 또는 팀)가 데이터베이스 생성과 연동 조회에도 충분하다고 봅니다. 부족하면 구현 때 확인해 발급 안내를 보완합니다.

## Off-limits

- 로그인과 사용자별 비공개 데이터 — 사용자별 권한 규칙과 생성 코드의 보안 검증이 이번 범위를 넘습니다.
- 서버에 접근 권한 저장 — [credential-storage](../../decisions/credential-storage.md)가 금지합니다.
- Supabase와 그 밖의 외부 데이터베이스 계정, 새 토큰 입력 — 사용자가 Supabase를 쓰지 않기로 했고, Neon으로 정했습니다. — [server-data-storage](../../decisions/server-data-storage.md)
- 파일·사진 저장, 실시간 갱신, 데이터 내보내기와 백업 — 입력한 텍스트 데이터의 저장과 조회까지만 합니다.
- 표 구조를 바꾼 뒤 기존 데이터 유지, 구현 뒤 Spec 변경에 따른 다시 만들기 — 앞선 결과와 같이 "다시 확인" 표시와 안내까지만 합니다.
- 데이터를 보는 관리 화면, 데이터베이스 삭제·정리 — 사용자가 Vercel 대시보드에서 직접 합니다.
- 기존 데이터베이스 선택과 여러 시스템의 데이터베이스 공유 — 시스템마다 새 데이터베이스만 만듭니다.
- 메일·메신저 발송, 예약 실행, 키가 필요한 외부 서비스 — 이후 결과로 미룹니다.

## Deferred

- 로그인과 사용자별 비공개 데이터 — 로그인이 들어오는 결과를 shape할 때 다시 엽니다. 임시 동작: 공유 데이터만 만들고, 사용자별 비공개 데이터가 필요한 Spec은 구현을 막고 이유를 안내합니다.
- Neon 연동 설치의 자동화 — 구현 전 확인에서 API로 설치까지 되는 것이 확인되면 다시 엽니다. 임시 동작: 사용자가 Vercel 대시보드에서 한 번 설치합니다.
- 데이터베이스 하나를 여러 시스템이 나눠 쓰기 — 무료 플랜의 데이터베이스 수 한도 때문에 시스템을 만들지 못한다는 사례가 실제 사용에서 반복되면 다시 엽니다. 임시 동작: 시스템마다 새 데이터베이스를 만들고, 한도에 걸리면 이유를 안내하고 멈춥니다.
- 메일·메신저 발송, 예약 실행, 키가 필요한 외부 서비스 지원 — 앞선 결과의 Deferred를 따르며, 이 결과가 출시된 뒤 사용자가 요구하는 재료를 본 뒤 다시 엽니다. 임시 동작: 해당 Spec은 구현을 막고 이유를 안내합니다.

## Remaining risks

- 공유 데이터에는 로그인이 없어서 주소를 아는 누구나 데이터를 읽고 고치고 지울 수 있습니다. 이름·연락처 같은 개인 정보를 받는 시스템을 만들면 노출될 수 있습니다. 구현 시작 전 안내와 "만들고 올리기" 확인으로 알리지만, 사용자가 이를 놓칠 수 있습니다.
- Neon 연동을 대시보드에서 한 번 설치해야 하는 단계에서 비개발자가 이탈할 수 있습니다. 이 설치를 API로 대신할 수 있는지, 서비스가 설치 여부를 어떻게 확인하는지는 공식 문서로만 일부 확인했고 직접 실행해 보지 않았습니다.
- 무료 플랜의 데이터베이스 수 한도, 데이터베이스가 준비되기까지의 시간, 결제 수단이 없는 계정에서의 응답(문서상 402), 표를 만드는 방법의 세부 동작도 구현 전에 확인해야 합니다.
- agent가 만든 서버 코드는 서비스가 직접 실행해 보지 못하고 빌드와 배포 뒤 확인으로만 검증합니다. 빌드가 통과해도 저장과 조회가 Spec대로 동작하지 않을 수 있습니다.
- 서버 코드와 환경 변수, 외부 패키지를 허용하면 생성 코드의 빌드 실패와 보안 실수(비밀 키 노출) 가능성이 커집니다. 노출은 코드 검사로 막지만 모든 경우를 잡지는 못합니다.
- 브라우저 데이터를 지우면 결과 주소가 사라집니다. 데이터베이스와 데이터는 사용자 계정에 남아 있습니다.
- agent 구현 품질은 모델과 프롬프트에 따라 흔들립니다. 앞선 결과에서 같은 종류의 eval 목표를 처음 값으로 달성하지 못했던 경험이 있어, 위 목표에 못 미치면 확정 전에 목표나 방법을 다시 정해야 할 수 있습니다. 새 갈래 판정의 목표(85%)는 agent가 정한 값입니다.

## Setup before implementation

- 앞선 결과의 Vercel 테스트 계정과 토큰으로 Neon 연동 설치 — 데이터베이스 생성의 전제입니다. 완료 조건: 테스트 Vercel 팀에 Neon 연동이 설치되어 있고, 그 토큰으로 앱 밖에서 Vercel API를 호출해 연동 설정 목록에서 Neon이 조회되는 것.
- 토큰의 데이터베이스 생성·연결 권한 확인 — 완료 조건: 그 토큰으로 앱 밖에서 Vercel API를 호출해 테스트 프로젝트에 새 Neon 데이터베이스를 만들고 프로젝트에 연결해 환경 변수가 들어가는 것을 확인한 뒤, 데이터베이스를 삭제할 수 있는 것.
- 구현자가 쓸 테스트용 Azure OpenAI 연결 정보와 GitHub OAuth 앱 — 앞선 결과에서 준비한 것을 그대로 씁니다. 완료 조건은 [guided-implementation-to-deploy](../guided-implementation-to-deploy/spec.md)의 Setup과 같습니다.
