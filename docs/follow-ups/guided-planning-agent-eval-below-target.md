# agent 대화 품질 eval이 처음 목표(아이디어 90%, 첫 Spec 90%)에 못 미치고, 조정한 목표 위에서 올릴 여지가 남아 있다

**Symptom**: 최종 판정용 20개 사례(반복 2회)에서 아이디어 추천 통과가 74%(14/19회), 첫 Spec 크기 통과가 79%(31/39회)로, 스펙 목표(재료 사례 10개 중 9개, 20개 중 18개)에 못 미친다. 질문 수 기준(96%)만 목표를 넘는다.

**Observed evidence**: `.claude/hillclimb/guided-planning-to-spec/run.ts`를 `--variant v7 --split test --reps 2`로 실행한 결과(Azure OpenAI 배포, 판정은 claude CLI). 사례와 판정 기준은 `docs/specs/guided-planning-to-spec/eval-cases.jsonl`, `eval-criteria.md`. baseline은 아이디어 9/20회, Spec 24/40회였고 튜닝 7라운드 뒤 v5와 v7이 같은 수준에서 멈췄다. 실패한 시도의 판정 이유를 사람이 다시 읽은 결과는 아래 "Suspected cause"에 적었다.

**Suspected cause**: 판정 기준을 다시 점검해 보니 두 기준의 실패 성격이 다르다.

- 아이디어 추천(실패 5회): 진짜 위반은 1회(m08, 고르지 않은 '문화행사' 필요)뿐이고, 나머지 4회는 심사자가 "필요할 수 있다"는 추측으로 실패 판정을 냈다. 예: m07은 '사진 읽기'와 '사용자가 남긴 기록'을 둘 다 골랐는데 "기록이 필요하다"며 실패시켰고, m08#0은 고른 재료에 없는 "위치 정보 기능"을 심사자가 만들어 냈다. 심사 지시에 "명시적으로 필요한 경우만 실패"라는 문구가 없어 과엄격하다.
- 첫 Spec 크기(실패 8회): 대부분 실제 결함이다. 범위에 별개 결과가 섞임(i01의 "팀원과 공유", m10#1의 결과 둘), 확인 방법이 앱 밖 행동(m09 "실제로 가서 즐겨본다")이거나 막연함(i01, i08의 "잘 나오는지", "정확한 내용"). 다만 m05와 m10은 "매일/월말 이메일이 오는지"처럼 시간이 지나야 확인되는 방법을 `right_size` 위반으로 처리했는데, 승인된 프로토타입의 예시 Spec("등록 다음 날 7시에 알림이 오는지")도 같은 형태라 이 기준이 스펙 의도보다 엄격할 수 있다.
- 모델 한계 여부는 확인하지 않았다.

**What was tried**: 재료별 규칙과 좋은·나쁜 예시를 프롬프트에 넣고, 아이디어와 Spec 응답을 코드로 검사해 어긋나면 최대 두 번 다시 받게 했다. 점수는 baseline보다 올랐지만 목표에는 닿지 않았다. 판정 기준과 사례는 바꾸지 않았다.

**재채점 결과(심사 지시 v2, 사용자 승인 후 저장된 trace로 다시 채점)**: 같은 최종 판정용 20사례를 새 지시로 채점했다. 아이디어 추천은 v7이 18/19회(95%, 사례 10개 중 9개를 매번 통과)로 목표를 넘었고 baseline은 12/20회(60%)다. 첫 Spec 크기는 v7이 5/39회(13%), baseline이 3/40회(8%)로 오히려 크게 떨어졌다. 이유는 새 지시가 "막연한 확인 방법은 실패"를 분명히 하자, 거의 모든 Spec의 두 번째 `verification`("기록이 잘 되었는지 확인한다", "올바른 통화가 반영되는지 확인한다", "기상청 수치와 비교한다")이 실패로 잡혔기 때문이다. 즉 이 결함은 이전 심사에서 가려져 있던 실제 문제다. 이전 점수(79%)와는 기준이 달라 비교할 수 없다.

**v9 결과(심사 지시 v2, 최종 판정용 20사례 x2회)**: 막연한 확인 방법 검사를 넓히고(잘 되었는지, 올바른, 정확, 비교, 일치), 확인 방법이 결과와 범위에 없는 기능(알림 전송, 다른 사람)을 확인하지 못하게 하는 검사와 프롬프트 규칙을 더했다. 아이디어 추천 19/20회(95%, 사례 9/10 매번 통과), 질문 최대 하나 96%(306/320)로 둘은 목표를 넘었다. 첫 Spec 크기는 19/40회(48%, 사례 20개 중 4개만 매번 통과)로, 같은 기준의 baseline 8%와 v7 13%보다 크게 올랐지만 목표(20개 중 18개)에는 멀다. 튜닝용 사례는 v8 47%, v9 19%로 오르내려 잡음이 크다.

**남은 실패(v9 held-out 21회)**: (1) 두 번째 `verification`이 여전히 막연함("잘 추가되는지", "잘 정리됐는지", "맞는지 확인", 원본과 비교) (2) `result`나 `scope`에 별개 결과가 섞임(i02, i03, i08, m07) (3) 외부 사건을 기다려야 하는 확인("환율이 설정값 아래로 떨어지면 알림이 오는지")을 심사자가 `right_size` 위반으로 처리(m06). (3)은 알림 아이디어의 본질적 확인이라 심사 기준을 더 손봐야 할 수 있다.

**v10·v11 결과(최종 판정용 20사례 x2회, 심사 지시 v2)**: v9의 검사를 더 조였다(확인 방법 2개 이하, 화면·알림에서 보이는 것 필수, 외부 상황 대기 확인 금지, 결과에 일 이어붙임 금지). v10은 프롬프트의 "~한다 하나" 문구 탓에 모델이 `result` 끝에 "하나"를 붙여 첫 Spec 크기 13/39회(33%), 아이디어 추천 84%로 떨어졌다. 문구를 고친 v11은 첫 Spec 크기 19/39회(49%, 사례 5/20 매번 통과), 아이디어 추천 17/19회(89%, 사례 8/10), 질문 95%로 v9(48%, 95%, 96%)와 같은 수준이다. 코드 검사를 조이는 방식은 첫 Spec 크기에서 약 50%에서 멈췄다.

**남은 실패(v11)**: 실패 20회 중 right_size 위반이 19회, single 위반이 5회다. right_size는 대부분 두 번째 `verification`을 심사자가 막연하다고 보는 경우이고, 코드 검사가 통과시킨 "화면에 보인다" 형태도 포함된다(예: "결과가 화면에 보이는지"처럼 무엇이 보여야 하는지 없는 문장). 이는 코드 정규식으로 구분하기 어려워, 모델이 스스로 구체적인 문장을 쓰도록 하거나 `verification`을 하나로 제한하는 구조 변경이 필요해 보인다.

**v12 결과(최종 판정용 20사례 x2회, 심사 지시 v2)**: `verification`을 정확히 1개로 제한하고(코드 검사와 프롬프트) 구체적인 값을 요구했다. 첫 Spec 크기는 24/39회(62%, 사례 8/20 매번 통과, 17/20는 한 번이라도 통과)로 v9(48%), v11(49%)보다 올랐다. 아이디어 추천은 16/20회(80%, 사례 7/10), 질문은 97%다. 아이디어 추천 코드는 v7 이후 바꾸지 않았는데 74~95% 사이에서 움직여, 이 표본(재료 사례 10개 x2회)의 잡음이 약 ±15점이라는 뜻이다. 목표 달성 여부를 한 번의 측정으로 단정하기 어렵다.

**남은 실패(v12)**: 첫 Spec 실패 15회 중 right_size 위반이 14회, single 위반이 3회다. right_size는 `verification`이 1개로 줄었는데도 심사자가 "무엇을 보면 되는지 불분명" 또는 scope가 확인 방법과 안 맞는다고 보는 경우가 많다. single 위반은 `scope`에 사용자가 늘리려던 '기록'이 섞이는 경우(i06, i08)다. 이 두 유형이 코드 검사로 더 줄지는 불확실하다.

**목표 조정(2026-11-19 사용자 승인)**: 스펙의 목표를 아이디어 추천 "재료 사례 반복 합산 통과율 80% 이상", 첫 Spec 크기 "20개 사례 반복 합산 통과율 60% 이상"으로 낮췄다(질문 90% 이상은 유지). 마지막 측정(v12)은 아이디어 추천 80%, 첫 Spec 크기 62%, 질문 97%로 조정된 목표를 간신히 넘지만 잡음(±15점) 안이라 안정적으로 넘는지는 확인하지 않았다.

**v12 안정성 재측정(2026-11-19, 코드 변경 없음, 최종 판정용 20사례 x2회 x2번)**: 프롬프트와 spec-guard가 v12와 같은 코드로 두 번 더 돌렸다(`results/v12-r2`, `results/v12-r3`). 아이디어 추천은 80%(16/20), 94%(16/17)로 v12 포함 세 번 합쳐 48/57회(84%)이고, 질문은 96~97%로 안정적이다. 첫 Spec 크기는 62%(24/39), 53%(21/40), 28%(10/36)로 세 번 합쳐 55/115회(48%)이며, 범위가 28~62%로 넓다. 즉 아이디어 추천과 질문은 조정된 목표(80%, 90%)를 안정적으로 넘지만, 첫 Spec 크기 60%는 v12의 62%가 운 좋은 표본이었고 안정적으로 넘지 못한다. r3에는 오류 4건(Azure 연결 실패 2건, 판정 JSON 파싱 실패 2건)이 있어 36회만 채점됐다. 한 측정이 다른 측정과 잡음 이상으로 다르므로, 구조 변경의 효과를 보려면 변경마다 2~3회 측정이 필요하다.

**v13 결과(최종 판정용 20사례 x2회 x2번, 현재 Azure 배포, 심사 지시 v2)**: 강한 모델 배포는 선택할 수 없어 (b)는 하지 않았다. v12 실패 trace에서 심사자가 "설정 직후 시험 알림"을 `scope`에 없는 기능으로 처리하고, `scope`에 있는데 `verification`이 확인하지 않는 항목(m04의 장르 선택, 목록 보기)도 실패시키는 것을 확인했다. 그래서 `verification`을 먼저 정하고 `scope`를 그 흐름을 쪼갠 2~3개로 만들게 했고(상한 3), 알림형은 `scope` 마지막에 시험 알림 항목을 넣게 했다. 첫 Spec 크기는 18/38(47%), 22/38(58%)로 합산 40/76회(53%)다. v12 세 번 합산(48%)보다 5점 올랐지만 잡음(±15점) 안이라 개선이라고 단정하기 어렵고, 조정된 목표 60%에도 못 미친다. 아이디어 추천은 35/38회(92%), 질문은 98~99%로 v12(84%, 96~97%)보다 높다. 오류는 측정마다 2건씩(연결 실패 또는 판정 JSON 파싱)이었다. 90%까지는 거리가 멀고, 코드 검사와 프롬프트 수정만으로는 50%대에서 멈추는 경향이 이어졌다.

**v14 결과(v13에서 시험 알림 유도를 되돌린 상태, 최종 판정용 20사례 x2회 x2번)**: v13이 알림 아이디어에서 `scope`에 시험 알림 항목을 넣게 한 것은 사용자가 원한 적 없는 기능을 Spec에 넣어 심사를 맞추는 일이라 요구와 맞지 않아 되돌렸다. 프롬프트의 시험 알림 문구, 시험·테스트 확인 차단, 외부 상황 대기 금지 검사와 그 테스트를 뺐고, `verification` 먼저·`scope` 상한 3은 남겼다. 알림 결과는 "등록 다음 날 아침 7시에 … 한 통이 온다"처럼 도착 시점을 적게 했다. 첫 Spec 크기는 27/40(68%), 21/39(54%)로 합산 48/79회(61%)다. 실패 31회 중 right_size 위반이 30회, single 위반이 1회다. 아이디어 추천은 37/40회(93%), 질문은 97~98%다. 합산은 조정된 목표(60%)를 넘지만 두 번의 점수가 14점 차이이고 표본이 작아 안정적으로 넘는다고 단정하기 어렵다. 같은 코드에서 v12는 28~62%였다. 시험 알림으로 우회하지 않고도 v12(48%)보다 높게 나왔지만 잡음 범위 안이다.

**심사 지시 v3와 v14 재채점(2026-11-19 사용자 지시)**: Spec 심사에 "문서에 명시된 내용만 근거로 삼고 추측은 false로 하지 않는다"를 넣고, 구현되지 않은 기능(로그인·계정·결제·사용자마다 다른 화면·여러 사람이 함께 쓰는 기능)이 `scope`에 있으면 실패가 아니라 보류로 빼서 별도 집계하게 했다(혼자 쓰는 서비스라서 로그인은 필요 없다). 저장된 v14 trace 두 묶음을 새 지시로 다시 채점한 결과 첫 Spec 크기는 35/39(90%), 34/39(87%)로 합산 69/78회(88%)다(심사 지시 v2에서는 61%). 보류 항목이 있는 Spec은 0/78회였다. v14 프롬프트가 이미 로그인·계정을 `scope`에 넣지 않게 하므로 보류는 점수에 영향이 없고, 올라간 것은 전부 추측 금지 효과다. 판정이 뒤집힌 건은 0→1이 23건, 1→0이 1건, 그대로 54건이다. 뒤집힌 건을 읽어 보면 대부분 "대여소가 몇 개 나올지 보장되지 않는다", "입금 데이터를 어떻게 넣는지 `scope`에 없다"처럼 문서에 없는 것을 추측한 실패였다. 다만 m07(`scope`에 "지출 정보를 입력한다"가 있는데 `result`는 자동 생성), i04(확인 방법이 `result`와 어긋남)처럼 실제 불일치였던 건도 통과로 바뀌었다. 이 점수는 기준이 달라져서 이전 점수와 비교할 수 없고, 모델이나 프롬프트가 좋아졌다는 뜻이 아니다. 실패 9회는 right_size 5회, single 3회, 그 외 1회다. 아직 정하지 않은 것: "구체적인 시점" 재정의와, 보류 항목을 앱에서 사용자에게 다시 묻는 동작(spec.md 수용 기준 변경)이다.

**심사 지시 v3 보강과 v14 재채점(2026-11-19 사용자 지시)**: "구체적인 시점"을 (1) 사용자가 하는 일, (2) 언제 확인하는지, (3) 무엇이 보이는지 세 요소로 정의했고, 알림 기능(메일, 메신저)은 없는 기능으로 보아 `scope`에 있으면 보류로 뺐다. 이 지시로 저장된 v14 trace 두 묶음을 다시 채점한 첫 Spec 크기는 35/40(88%), 31/39(79%)로 합산 66/79회(84%)다(직전 재채점은 88%). 보류 항목이 있는 Spec은 19/79회(24%)이고 m01, m03, m05, m06, i03에서 나왔다. 실패 13회는 right_size 12회, 그 외 1회다. 직전보다 right_size 실패가 5회에서 12회로 늘었다. 새 정의가 세 요소를 모두 요구해서, "목록이 화면에 보인다"처럼 사용자가 하는 일이 빠진 문장과 `scope`의 항목을 `verification`이 확인하지 않는 경우가 실패로 잡히기 때문이다. 일관성 문제도 확인했다. 메일이 `verification`에만 있고 `scope`에는 없는 m03, m05, m10은 보류가 아니라 실패로 처리되었고, "아침 7시에 미세먼지 정보를 확인한다" 같은 항목은 알림이 아닌데도 보류됐다. 보류 판정이 알림 문구를 직접 읽지 못하는 경우가 있다는 뜻이다. 기준이 계속 바뀌어 이전 점수와 직접 비교할 수 없다.

**알림 기능 제거와 마무리(2026-11-19 사용자 지시)**: 알림(메일, 메신저 메시지)은 없는 기능이라 앱에서 Spec 전에 걸러낸다. 재료 목록에서 알림 묶음을 뺐고(`materials.ts`, PRODUCT.md, spec.md), 아이디어 추천 프롬프트와 `idea-guard.ts`가 알림·메일·메신저로 보내는 아이디어를 다시 쓰게 하며, 2·3단계 프롬프트는 사용자가 알림을 원하면 "알림은 아직 지원하지 않아요"라고 알리고 화면에서 직접 보는 형태로 바꾸게 한다. 시험 알림 유도는 이미 걷어냈다. 단위 테스트 219개와 타입 검사가 통과했고, 브라우저에서 재료 목록이 세 묶음으로 보이는 것을 확인했다. **남은 일**: (1) 평가 사례 m01, m03, m05, m06, m10이 알림 재료(메일, 메신저)를 골라서 지금 앱에서는 고를 수 없는 재료를 쓴다. 사례를 새 재료로 바꾸거나 빼야 하고, 그러면 아이디어 추천 목표(재료 사례 10개)를 다시 재야 한다. (2) 알림을 걸러낸 프롬프트로 새로 측정하지 않았다. 마지막 측정은 v14이고 위 재채점은 알림이 있는 앱 기준이다. (3) 사용자가 직접 적은 아이디어에 알림이 들어 있을 때(i03 등)의 대화 흐름은 프롬프트로만 처리하며 eval로 확인하지 않았다.

**평가 사례 교체(2026-11-19)**: 알림 재료(메일, 메신저)를 쓰던 사례 7개를 앱에서 고를 수 있는 재료로 바꿨다. 최종 판정용 m01(날씨와 미세먼지, 글 요약), m03(문화행사, 사용자가 남긴 기록), m05(뉴스 검색, 글 요약), m06(환율, 데이터를 읽고 하는 추천), m10(환율, 사용자가 남긴 기록)과 프롬프트 다듬기용 tm01(날씨와 미세먼지, 장소 검색), tm02(뉴스 검색, 사용자가 남긴 기록)이다. 같은 id의 이전 측정 결과(v1~v14)는 다른 사례의 결과라 새 사례와 비교할 수 없다. 아이디어 추천과 첫 Spec 크기 점수는 새 사례로 다시 측정해야 한다. 남은 일 (1)은 이것으로 끝났고 (2), (3)은 그대로다.

**v15 결과(알림 제거 앱 + 교체한 새 사례, 심사 지시 v3, 최종 판정용 20사례 x2회 x2번)**: 알림을 걸러낸 프롬프트와 idea-guard, 알림 재료를 뺀 사례로 처음 측정했다(`results/v15`, `results/v15-r2`). 첫 Spec 크기는 28/37(76%), 34/37(92%)로 합산 62/74회(84%)이고, 보류 항목이 있는 Spec은 1/74회(i01)다. 실패 12회는 right_size 9회, single 3회다. 아이디어 추천은 17/18(94%), 13/18(72%)로 합산 30/36회(83%)다. 질문은 97%다. 오류가 측정마다 3건(JSON 파싱 또는 "agent의 답을 이해하지 못했어요", m06, i07, m05)이라 일부 사례가 빠졌다. 아이디어 추천 실패 6회를 읽어 보면 대부분 실제 위반이다. m08에서 고르지 않은 문화행사를 쓴 경우 2회, m01에서 고르지 않은 뉴스 검색의 기사를 가져오는 경우 1회, m03와 m10에서 기록을 바탕으로 골라 보여 주는 표현을 추천으로 본 경우 2회, m07에서 사진으로 주제를 골라 시리즈를 만드는 표현 1회다. 두 측정의 차이(첫 Spec 76% 대 92%, 아이디어 94% 대 72%)가 크다는 점은 이전과 같아 한 번의 측정으로 판단하기 어렵다. 조정된 목표(아이디어 80%, 첫 Spec 60%, 질문 90%)는 합산으로는 모두 넘지만, 아이디어 추천은 한 측정이 목표 아래이고, 사례와 심사 기준이 바뀌어 이전 점수와는 비교할 수 없다.
