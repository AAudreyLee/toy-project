# agent 대화 품질 eval이 아이디어 추천과 첫 Spec 크기에서 목표에 못 미친다

**Symptom**: 최종 판정용 20개 사례(반복 2회)에서 아이디어 추천 통과가 74%(14/19회), 첫 Spec 크기 통과가 79%(31/39회)로, 스펙 목표(재료 사례 10개 중 9개, 20개 중 18개)에 못 미친다. 질문 수 기준(96%)만 목표를 넘는다.

**Observed evidence**: `.claude/hillclimb/guided-planning-to-spec/run.ts`를 `--variant v7 --split test --reps 2`로 실행한 결과(Azure OpenAI 배포, 판정은 claude CLI). 사례와 판정 기준은 `docs/specs/guided-planning-to-spec/eval-cases.jsonl`, `eval-criteria.md`. baseline은 아이디어 9/20회, Spec 24/40회였고 튜닝 7라운드 뒤 v5와 v7이 같은 수준에서 멈췄다. 실패한 시도의 판정 이유를 사람이 다시 읽은 결과는 아래 "Suspected cause"에 적었다.

**Suspected cause**: 판정 기준을 다시 점검해 보니 두 기준의 실패 성격이 다르다.

- 아이디어 추천(실패 5회): 진짜 위반은 1회(m08, 고르지 않은 '문화행사' 필요)뿐이고, 나머지 4회는 심사자가 "필요할 수 있다"는 추측으로 실패 판정을 냈다. 예: m07은 '사진 읽기'와 '사용자가 남긴 기록'을 둘 다 골랐는데 "기록이 필요하다"며 실패시켰고, m08#0은 고른 재료에 없는 "위치 정보 기능"을 심사자가 만들어 냈다. 심사 지시에 "명시적으로 필요한 경우만 실패"라는 문구가 없어 과엄격하다.
- 첫 Spec 크기(실패 8회): 대부분 실제 결함이다. 범위에 별개 결과가 섞임(i01의 "팀원과 공유", m10#1의 결과 둘), 확인 방법이 앱 밖 행동(m09 "실제로 가서 즐겨본다")이거나 막연함(i01, i08의 "잘 나오는지", "정확한 내용"). 다만 m05와 m10은 "매일/월말 이메일이 오는지"처럼 시간이 지나야 확인되는 방법을 `right_size` 위반으로 처리했는데, 승인된 프로토타입의 예시 Spec("등록 다음 날 7시에 알림이 오는지")도 같은 형태라 이 기준이 스펙 의도보다 엄격할 수 있다.
- 모델 한계 여부는 확인하지 않았다.

**What was tried**: 재료별 규칙과 좋은·나쁜 예시를 프롬프트에 넣고, 아이디어와 Spec 응답을 코드로 검사해 어긋나면 최대 두 번 다시 받게 했다. 점수는 baseline보다 올랐지만 목표에는 닿지 않았다. 판정 기준과 사례는 바꾸지 않았다.

**재채점 결과(심사 지시 v2, 사용자 승인 후 저장된 trace로 다시 채점)**: 같은 최종 판정용 20사례를 새 지시로 채점했다. 아이디어 추천은 v7이 18/19회(95%, 사례 10개 중 9개를 매번 통과)로 목표를 넘었고 baseline은 12/20회(60%)다. 첫 Spec 크기는 v7이 5/39회(13%), baseline이 3/40회(8%)로 오히려 크게 떨어졌다. 이유는 새 지시가 "막연한 확인 방법은 실패"를 분명히 하자, 거의 모든 Spec의 두 번째 `verification`("기록이 잘 되었는지 확인한다", "올바른 통화가 반영되는지 확인한다", "기상청 수치와 비교한다")이 실패로 잡혔기 때문이다. 즉 이 결함은 이전 심사에서 가려져 있던 실제 문제다. 이전 점수(79%)와는 기준이 달라 비교할 수 없다.

**Proposed next step**: 첫 Spec 쪽을 고친다. `features/guided-planning/spec-guard.ts`의 막연함 검사가 "잘 되었는지", "올바른 …되는지", "비교한다"를 놓치므로 넓히고, 프롬프트에 "verification은 첫 항목처럼 화면에서 무엇을 보면 되는지 적고, 데이터 정확성이나 외부 값과 비교하는 항목은 넣지 않는다"를 더한 뒤 튜닝용 사례로 다시 측정한다. 아이디어 추천은 목표를 넘었으므로 건드리지 않는다. 그다음에도 Spec이 미달이면 더 강한 모델 배포로 같은 eval을 돌려 모델 한계인지 가르고, 그래도 안 되면 스펙 목표치를 조정한다(승인된 계약 변경이라 사용자 결정이 필요하다).
