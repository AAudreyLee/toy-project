# agent 대화 품질 eval이 아이디어 추천과 첫 Spec 크기에서 목표에 못 미친다

**Symptom**: 최종 판정용 20개 사례(반복 2회)에서 아이디어 추천 통과가 74%(14/19회), 첫 Spec 크기 통과가 79%(31/39회)로, 스펙 목표(재료 사례 10개 중 9개, 20개 중 18개)에 못 미친다. 질문 수 기준(96%)만 목표를 넘는다.

**Observed evidence**: `.claude/hillclimb/guided-planning-to-spec/run.ts`를 `--variant v7 --split test --reps 2`로 실행한 결과(Azure OpenAI 배포, 판정은 claude CLI). 사례와 판정 기준은 `docs/specs/guided-planning-to-spec/eval-cases.jsonl`, `eval-criteria.md`. baseline은 아이디어 9/20회, Spec 24/40회였고 튜닝 7라운드 뒤 v5와 v7이 같은 수준에서 멈췄다. 실패한 시도의 판정 이유를 사람이 다시 읽은 결과는 아래 "Suspected cause"에 적었다.

**Suspected cause**: 판정 기준을 다시 점검해 보니 두 기준의 실패 성격이 다르다.

- 아이디어 추천(실패 5회): 진짜 위반은 1회(m08, 고르지 않은 '문화행사' 필요)뿐이고, 나머지 4회는 심사자가 "필요할 수 있다"는 추측으로 실패 판정을 냈다. 예: m07은 '사진 읽기'와 '사용자가 남긴 기록'을 둘 다 골랐는데 "기록이 필요하다"며 실패시켰고, m08#0은 고른 재료에 없는 "위치 정보 기능"을 심사자가 만들어 냈다. 심사 지시에 "명시적으로 필요한 경우만 실패"라는 문구가 없어 과엄격하다.
- 첫 Spec 크기(실패 8회): 대부분 실제 결함이다. 범위에 별개 결과가 섞임(i01의 "팀원과 공유", m10#1의 결과 둘), 확인 방법이 앱 밖 행동(m09 "실제로 가서 즐겨본다")이거나 막연함(i01, i08의 "잘 나오는지", "정확한 내용"). 다만 m05와 m10은 "매일/월말 이메일이 오는지"처럼 시간이 지나야 확인되는 방법을 `right_size` 위반으로 처리했는데, 승인된 프로토타입의 예시 Spec("등록 다음 날 7시에 알림이 오는지")도 같은 형태라 이 기준이 스펙 의도보다 엄격할 수 있다.
- 모델 한계 여부는 확인하지 않았다.

**What was tried**: 재료별 규칙과 좋은·나쁜 예시를 프롬프트에 넣고, 아이디어와 Spec 응답을 코드로 검사해 어긋나면 최대 두 번 다시 받게 했다. 점수는 baseline보다 올랐지만 목표에는 닿지 않았다. 판정 기준과 사례는 바꾸지 않았다.

**재채점 결과(심사 지시 v2, 사용자 승인 후 저장된 trace로 다시 채점)**: 같은 최종 판정용 20사례를 새 지시로 채점했다. 아이디어 추천은 v7이 18/19회(95%, 사례 10개 중 9개를 매번 통과)로 목표를 넘었고 baseline은 12/20회(60%)다. 첫 Spec 크기는 v7이 5/39회(13%), baseline이 3/40회(8%)로 오히려 크게 떨어졌다. 이유는 새 지시가 "막연한 확인 방법은 실패"를 분명히 하자, 거의 모든 Spec의 두 번째 `verification`("기록이 잘 되었는지 확인한다", "올바른 통화가 반영되는지 확인한다", "기상청 수치와 비교한다")이 실패로 잡혔기 때문이다. 즉 이 결함은 이전 심사에서 가려져 있던 실제 문제다. 이전 점수(79%)와는 기준이 달라 비교할 수 없다.

**v9 결과(심사 지시 v2, 최종 판정용 20사례 x2회)**: 막연한 확인 방법 검사를 넓히고(잘 되었는지, 올바른, 정확, 비교, 일치), 확인 방법이 결과와 범위에 없는 기능(알림 전송, 다른 사람)을 확인하지 못하게 하는 검사와 프롬프트 규칙을 더했다. 아이디어 추천 19/20회(95%, 사례 9/10 매번 통과), 질문 최대 하나 96%(306/320)로 둘은 목표를 넘었다. 첫 Spec 크기는 19/40회(48%, 사례 20개 중 4개만 매번 통과)로, 같은 기준의 baseline 8%와 v7 13%보다 크게 올랐지만 목표(20개 중 18개)에는 멀다. 튜닝용 사례는 v8 47%, v9 19%로 오르내려 잡음이 크다.

**남은 실패(v9 held-out 21회)**: (1) 두 번째 `verification`이 여전히 막연함("잘 추가되는지", "잘 정리됐는지", "맞는지 확인", 원본과 비교) (2) `result`나 `scope`에 별개 결과가 섞임(i02, i03, i08, m07) (3) 외부 사건을 기다려야 하는 확인("환율이 설정값 아래로 떨어지면 알림이 오는지")을 심사자가 `right_size` 위반으로 처리(m06). (3)은 알림 아이디어의 본질적 확인이라 심사 기준을 더 손봐야 할 수 있다.

**v10·v11 결과(최종 판정용 20사례 x2회, 심사 지시 v2)**: v9의 검사를 더 조였다(확인 방법 2개 이하, 화면·알림에서 보이는 것 필수, 외부 상황 대기 확인 금지, 결과에 일 이어붙임 금지). v10은 프롬프트의 "~한다 하나" 문구 탓에 모델이 `result` 끝에 "하나"를 붙여 첫 Spec 크기 13/39회(33%), 아이디어 추천 84%로 떨어졌다. 문구를 고친 v11은 첫 Spec 크기 19/39회(49%, 사례 5/20 매번 통과), 아이디어 추천 17/19회(89%, 사례 8/10), 질문 95%로 v9(48%, 95%, 96%)와 같은 수준이다. 코드 검사를 조이는 방식은 첫 Spec 크기에서 약 50%에서 멈췄다.

**남은 실패(v11)**: 실패 20회 중 right_size 위반이 19회, single 위반이 5회다. right_size는 대부분 두 번째 `verification`을 심사자가 막연하다고 보는 경우이고, 코드 검사가 통과시킨 "화면에 보인다" 형태도 포함된다(예: "결과가 화면에 보이는지"처럼 무엇이 보여야 하는지 없는 문장). 이는 코드 정규식으로 구분하기 어려워, 모델이 스스로 구체적인 문장을 쓰도록 하거나 `verification`을 하나로 제한하는 구조 변경이 필요해 보인다.

**v12 결과(최종 판정용 20사례 x2회, 심사 지시 v2)**: `verification`을 정확히 1개로 제한하고(코드 검사와 프롬프트) 구체적인 값을 요구했다. 첫 Spec 크기는 24/39회(62%, 사례 8/20 매번 통과, 17/20는 한 번이라도 통과)로 v9(48%), v11(49%)보다 올랐다. 아이디어 추천은 16/20회(80%, 사례 7/10), 질문은 97%다. 아이디어 추천 코드는 v7 이후 바꾸지 않았는데 74~95% 사이에서 움직여, 이 표본(재료 사례 10개 x2회)의 잡음이 약 ±15점이라는 뜻이다. 목표 달성 여부를 한 번의 측정으로 단정하기 어렵다.

**남은 실패(v12)**: 첫 Spec 실패 15회 중 right_size 위반이 14회, single 위반이 3회다. right_size는 `verification`이 1개로 줄었는데도 심사자가 "무엇을 보면 되는지 불분명" 또는 scope가 확인 방법과 안 맞는다고 보는 경우가 많다. single 위반은 `scope`에 사용자가 늘리려던 '기록'이 섞이는 경우(i06, i08)다. 이 두 유형이 코드 검사로 더 줄지는 불확실하다.

**Proposed next step**: (a) 같은 eval을 두 번 더 돌려 v12의 실제 점수 범위(잡음)를 잡는다. (b) 더 강한 모델 배포로 같은 eval을 돌려 모델 한계인지 가른다. (c) 그래도 미달이면 스펙 목표치나 심사 기준을 조정한다(승인된 계약 변경이라 사용자 결정이 필요하다). 아이디어 추천과 질문 수는 목표 근처이므로 건드리지 않는다.
